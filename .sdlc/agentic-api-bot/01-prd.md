# PRD: Agentic API Task Execution (Multi-Level Tool Chains)

## Problem
Today an agent's Tool Execution Framework (`services/conversation/tools/`) can only call a small, hardcoded set of executors — `book_appointment`, `cancel_appointment`, `reschedule_appointment`, `send_sms` — each hand-written against one specific provider SDK (Cal.com, Twilio) and registered in code (`services/conversation/tools/registry.py`). Adding any new capability requires an engineer to ship a new executor class; a tenant cannot expose their own backend/CRM/ticketing API to their agent without an engineering change. The orchestrator (`services/conversation/tools/orchestrator.py`) also caps iteration at `DEFAULT_MAX_TOOL_ITERATIONS = 2` and treats every tool call as independent — it has no concept of one call's result being *required input* to a later call beyond what fits in one extra LLM round-trip, and no way to fail one specific step in a chain without discarding the whole turn's progress. A tenant who wants "look up the caller's account, then use the account ID to check their order status, then use the order ID to trigger a refund" cannot build that today at any layer — RAG retrieval answers questions about content, and the fixed executors don't compose.

## Scope
- In: A tenant admin can define a custom API-backed tool (name, description, request shape, auth) without an engineer writing an executor, scoped to their own tenant, the same way `tool_provider_configs`/`agent_tool_policies` already scope Cal.com/Twilio tools today.
- In: An agent enabled for a custom API tool can have the LLM call it mid-conversation, exactly like `book_appointment` is called today (same `ToolCallOrchestrator.run_turn()` path, same `ToolResult`/`ToolStatus` contract).
- In: A tenant can chain multiple custom API tools where a later call's input is populated from an earlier call's output (e.g., a returned `account_id` becomes the request field for the next call), at least several levels deep in a single conversational turn — not just the current one-hop tool→LLM→one-more-tool pattern.
- In: When any call in a chain fails, the caller gets an honest, in-character response about what could and couldn't be completed — never a fabricated "done" for a step whose downstream dependency failed (same non-fabrication posture already enforced for bookings — see `pipeline.py`'s `_claims_booking_without_tool_call`).
- In: An operator/admin can see, per call, which API tools were invoked, in what order, with what result, sufficient to debug a failed chain after the fact.
- Out: A visual chain-builder / no-code UI for wiring dependencies — this PRD covers the tenant being able to configure a chain-capable tool and have it execute correctly; the authoring UX (drag-and-drop vs. JSON vs. spreadsheet import) is a separate design decision.
- Out: Replacing or modifying the existing hardcoded calendar/SMS executors — they continue to work unchanged; this is an additive capability alongside them.
- Out: RAG/knowledge retrieval changes — retrieval (`services/knowledge/`) is unaffected; this PRD is scoped to the tool-calling side of a turn, not the retrieval side.
- Out: Cross-tenant or cross-agent tool sharing — a configured API tool is only ever usable by the tenant that owns it, same isolation `tool_provider_configs.tenant_id` already enforces.

## Acceptance criteria
1. Given a tenant admin configures a custom API tool (name, endpoint, method, request schema, auth reference) for their tenant, when they enable it on one of their agents, then that agent's next call offers the tool to the LLM in the same tool-schema list as the built-in tools.
2. Given an agent has a custom API tool enabled, when the caller's request requires it, then the LLM calling that tool executes a real HTTP call and the caller hears a response derived from the real result — never a narrated success with no call made (same class of check as today's fabricated-booking guardrail).
3. [Pending open question 1 — LLM-decided vs. pre-declared chain] Given a chain of two or more custom API tools where tool B's input schema references a field produced in tool A's output, when tool A succeeds, then tool B is invoked with that field populated from A's actual response — not a value the LLM invents independently.
4. [Pending open question 1 — LLM-decided vs. pre-declared chain] Given a chain of 3+ dependent API calls, when every call in the chain succeeds, then the final response to the caller reflects the outcome of the full chain, not just the last call in isolation (e.g., it can reference what was looked up in step 1 while confirming what happened in step 3).
5. Given a chain where an intermediate call fails (timeout, non-2xx, malformed response), when the chain cannot proceed because a later step's required input was never produced, then the caller is told the operation could not be completed — the agent never claims a downstream step succeeded.
6. Given a chain where an intermediate call fails, when a partial result was already produced by an earlier successful call, then that partial state is not silently lost — the turn's response and the persisted record both reflect what did and didn't complete.
7. Given an API call in a chain times out, when the configured per-tool timeout (mirroring `agent_tool_policies.timeout_ms`) elapses, then the chain stops at that step with a `TIMEOUT` result and does not retry indefinitely or hang the turn.
8. Given a caller barges in (interrupts) while a multi-step chain is mid-execution, when the interruption is detected, then the in-flight chain is handled the same way a single in-flight tool call is handled today (stop waiting on it; do not resurrect it into a stale turn) — the multi-step case must not bypass existing barge-in behavior.
9. Given an agent has no custom API tools enabled, when a turn runs, then behavior is byte-identical to today — no added latency, no schema offered, same as the existing "no tools enabled" default.
10. Given a custom API tool belonging to Tenant A, when Tenant B's agent tries to reference or enable it, then the request is rejected — tool visibility is tenant-scoped exactly like `tool_provider_configs.tenant_id` scopes existing tools.
11. [Pending open question 1 — LLM-decided vs. pre-declared chain] Given a chain would require more dependent calls than the platform's configured maximum depth, when that depth is exceeded, then execution stops with a clear, non-fabricated failure rather than looping or silently truncating the chain without telling the caller anything completed.
12. Given a custom API tool's configured auth reference (`api_key_ref`) is invalid or the credential is missing, when the tool is invoked, then the call fails as `UNAVAILABLE`/`FAILED` (never sends a request with no credential and never leaks the credential reference itself in any user-facing or logged response).
13. [Pending open question 1 — LLM-decided vs. pre-declared chain] Given two independent (non-dependent) API tools are both enabled and relevant to the same turn, when the LLM calls both, then they execute exactly as sequential/independent tool calls do today — a chain is only inferred where an explicit dependency exists, never assumed between two unrelated tools.
14. Given a completed or failed multi-step chain, when an operator inspects that call's tool-call history afterward, then every step's tool name, arguments used (including which came from a prior step's output), and result status are visible and attributable to that specific call, subject to the redaction constraint below.
15. Given a chain step has already executed a side-effecting (non-idempotent) call successfully, when a later step in the same chain fails and the turn/chain is re-invoked (by the LLM, the caller repeating themselves, or any retry path), then the already-completed side-effecting step is not automatically re-executed — either it is invoked with the same idempotency key so a duplicate is safely rejected/deduped by the downstream API, or the framework refuses to auto-retry a chain past a completed side-effecting step and requires a fresh, explicit tool call instead.

## Constraints
- Must build on the existing Tool Execution Framework, not replace it: `ToolRegistry` (`services/conversation/tools/registry.py`), `ToolPolicyResolver` (`services/conversation/tools/policy_resolver.py`), `ToolCallOrchestrator.run_turn()` (`services/conversation/tools/orchestrator.py`), and the `ToolResult`/`ToolStatus`/`ToolExecutionContext` contracts (`services/conversation/tools/types.py`) are the seams a chained-API capability must compose with, not duplicate.
- Tenant scoping must match `tool_provider_configs.tenant_id` and per-agent enablement must match `agent_tool_policies` (`agent_id`, `enabled`, `UNIQUE (agent_id, tool_name)`) in `database/schema.sql` — a new API-tool concept must not introduce a second, unscoped path to tool visibility (lesson: an unscoped index/config is a cross-tenant leak, see `.claude/sdlc/lessons.md` #3).
- `api_key_ref` must stay a reference only (`'env:...' | 'enc:...' | 'k8s:...'`), never a literal secret in the database, in logs, or in any tool-call-history view — same discipline `tool_provider_configs.api_key_ref` already documents.
- The tool-call history view required by AC 14 must redact sensitive payload data, not just credential references: any argument or response field flowing between chain steps (e.g., an account ID, order ID, or other tenant-supplied business data) is subject to whatever the tenant/tool configuration marks sensitive, and at minimum must never be logged or displayed in plaintext anywhere a credential reference itself is already forbidden from appearing (see the `api_key_ref` constraint above) — visibility for debugging (AC 14) and redaction of sensitive values are both required, not in tension, and a tool's schema must let an admin flag which fields are sensitive.
- Every side-effecting (non-idempotent) chain step must carry an idempotency key derived the same way `ToolExecutionRequest.idempotency_key` already defaults to `tool_call_id` (see `types.py`'s `__post_init__`) — re-invocation of a chain must never re-execute a completed side-effecting step under a new, distinct key; retry, if supported at all, must reuse the original key so the downstream API can dedupe, and any step the framework cannot prove is idempotent-safe must fail closed (no automatic re-run) rather than risk a duplicate mutation (e.g., a second refund).
- The orchestrator's non-fabrication posture (never speak a success the tool didn't actually return) must extend to every step of a chain, not just the final call — this is the same class of guarantee `pipeline.py`'s booking-fabrication detector already enforces for `book_appointment` and must not regress for chained calls.
- `DEFAULT_MAX_TOOL_ITERATIONS` / per-tool `timeout_ms` and `max_calls_per_turn` (`agent_tool_policies` columns) are the existing per-turn ceilings; a chain-depth limit must compose with these, not silently bypass them and let a turn run unbounded.
- Barge-in/cancellation handling for an in-flight call (`asyncio.wait` race against `cancel_event` in `orchestrator.py`'s `_execute_tool_call`) must continue to apply to each step of a chain — a chain must not become a way to make an uninterruptible tool call.
- Any authenticated identity can currently call the knowledge service's internal retrieval endpoints (`services/knowledge/routers/retrieve.py`); a new API-tool-configuration surface is an admin-facing capability and must sit behind the same role/auth checks `services/config/auth.py`'s `CurrentUser` (tenant_id-scoped, `None` == superadmin) already applies to other tenant-scoped config, not a bare `get_current_user` check (lesson: adding a new capability to "any authenticated user" silently grants it everything guarded only by that dependency, see `.claude/sdlc/lessons.md` #4).

## Open questions
1. Does "multi-level dependencies" mean the LLM decides the chain dynamically per turn (it sees tool A's result and chooses to call B), or does a tenant admin pre-declare a fixed chain/DAG (A always feeds B always feeds C) that the orchestrator executes deterministically without an LLM decision at each hop? This changes whether the work is primarily prompt/orchestration or a new declarative chain-definition schema, and changes acceptance criteria 3, 4, 11, and 13 above materially — those four are tagged pending this decision and may need rewording once it's made.
2. What is the maximum chain depth the platform should enforce (AC 11), and is it a fixed platform constant or a per-tenant/per-agent configurable ceiling like `agent_tool_policies.max_calls_per_turn`?
3. For a custom tenant API tool, what auth schemes must be supported beyond the existing `api_key_ref` model (bearer token, OAuth2 client-credentials, per-call signed request) — this determines whether `tool_provider_configs.extra`'s existing free-form JSONB shape is sufficient or a new schema is needed?
