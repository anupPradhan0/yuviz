# Tasks: Invite-based user onboarding (Platform / Tenant)

## Phase 1: Schema (ordered, idempotent SQL steps — no migration tool)
This follows the repo's existing idempotent-SQL convention (`database/schema.sql`, applied in order — see CURSOR.md), expressed as ordered `ALTER`/`CREATE ... IF NOT EXISTS` steps rather than a new migration tool. T1-T5 are reviewed and merged as one atomic `schema.sql` apply — they are not five independently deployable production states (T2 alone, for instance, leaves `users.email` with no uniqueness guard at all until T4 lands); they are kept as separate tasks only so each step is reviewable and individually re-runnable/idempotent within that single apply.

## Phase 3: API, email delivery and cutover (invite routers reachable, old path retired)
Email delivery is built here, before the routers that need it, so the router's own "done when" (`email_sent: bool`) is satisfiable the moment this phase lands — not dependent on a later phase. `POST /users` is deleted at the end of this phase, once `POST /invites` + accept are mounted and reachable, so the system is never left without any account-creation path.

- [x] T16 Add `POST /invites`, `GET /invites` (super_admin sees all, tenant-scoped actor's `?tenant_id=` ignored/forced to JWT), `POST /invites/{id}/resend`, `POST /invites/{id}/revoke`, all under `require_role("superadmin","admin")`; the create/resend handlers call `send_invite_email()` after commit, non-fatal on failure — `services/config/routers/invites.py` (new) — done when: `GET /invites?tenant_id=<other>` as a tenant_admin returns only the actor's own tenant's invites (AC11); the same call as super_admin, unfiltered, returns invites across tenants; `POST /invites` returns 201 with `email_sent: bool` in the body; and with SMTP mocked to raise, `POST /invites` still returns 201 `email_sent: false` with the row `status='pending'` and resendable (AC12).
