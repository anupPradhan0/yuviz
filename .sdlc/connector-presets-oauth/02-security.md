# Security review: .sdlc/connector-presets-oauth/02-design.md (round 5, re-check of round-4 fixes)
VERDICT: GREEN

All five round-4 findings are CLOSED, each by a named mechanism I could trace to a real file, function or SQL predicate. Nothing cross-tenant and nothing privilege-related is open. What is left is three lows, two of which are new surface the revision itself introduced (a disconnect response that varies with another tenant's state, and an unenumerated call site of the new required `allow_pointer_schemes` keyword) plus one operator-safety gap on the quarantine script. None is a tenant-isolation break; none blocks the build. The round-4 finding-5 residual is a stated, bounded acceptance with an explicit unacceptability condition, which is the honest resolution and not an open flaw.

## Round-4 findings, re-verified

- **F1 (high, cross-tenant Config ciphertext) — CLOSED.** The script now acts, not counts. Quarantine covers all five columns (`custom_apis.auth_config`, `provider_configs.api_key_ref`, `tool_provider_configs.api_key_ref`, every `enc:` scalar/list entry of `telephony_configs.credentials`, `carriers.auth_token_ref`), in *every* occurrence including the original holder's, with the attribution argument stated rather than assumed (no column in this DB dates a credential's arrival; `audit._redact` at `services/config/audit.py:27` has always stripped `api_key_ref`/`auth_token_ref`, which I confirmed — so no "oldest wins" heuristic is available). The written value `"quarantined"` genuinely fails closed everywhere I traced it: `CompositeSecretResolver.resolve` raises on a scheme-less ref (`libs/config_sdk/secret_resolver.py:85-98`), `services/did/provider_manager.py:92` only skips resolution on a falsy ref so `"quarantined"` reaches the raise, and `services/telephony/accounts.py:138`'s direct `decrypt_secret` raises. Writes are conditional `UPDATE … WHERE id = $1 AND <col> = $2` on the exact old string with zero-rows aborting the whole transaction (lesson 8), under `LOCK TABLE … SHARE ROW EXCLUSIVE` across all five tables so no concurrent Config write interleaves. `main` exits 1 unless `remaining == 0 AND config_shared == 0`, so the gate is a readable value and not a promise; `--report` is 0600 JSONL, ids only, written after commit.
- **F2 (medium, `carriers.auth_token_ref`) — CLOSED.** Carriers is the fourth table everywhere the other three appear: `resolve_api_key_input(auth_token, auth_token_ref, current_ref=old[...], allow_pointer_schemes=…)` behind a `SELECT … FOR UPDATE` in `update_carrier`, `public_carrier(..., masked=ref_mask_required(current_user))` on list/get/create/update, new plaintext `auth_token: SecretStr` on `CarrierCreate`/`CarrierUpdate` (necessary, since carriers had no plaintext input at all), `auth_token` added to `audit._SECRET_REF_FIELDS`, the false docstring claim at `services/config/carriers.py:8-10` rewritten, and the admin-UI form row added so masking does not 400 on save. The column set is mechanized as `_CONFIG_REF_COLUMNS` with an `information_schema.columns` tripwire (lesson 29/42) — the right answer to the fact that two of four rounds were a missed ref table. I checked the one deliberately cross-tenant carrier read, `carriers.get_carrier_by_id(platform_scoped=…)` (`services/config/carriers.py:24-40`): it selects `platform_conn` only for a platform-scoped actor, so no tenant principal reads another tenant's ref.
- **F3 (medium, WhatsApp recipient) — CLOSED.** The recipient is `source='caller_id'`, `sensitive=true` on all three providers, fed only by `executor._remote_party` from server-stamped call metadata; `caller_arguments` is never read for such a param and `policy_resolver.py:255`'s `p.source = 'caller'` join (verified in the file) keeps the field out of the model's tool schema entirely. `value_digits_only` only strips the leading `+` from an already-normalized value and is CHECK-bound to `source='caller_id'`, so it cannot reshape the number. The cap query is correct against the real schema: `api_chain_steps.session_id` exists and is written from `request.session_id` on every step record (`executor.py:782,885,905,963-977`), `status='success'` is only written after a 2xx (`:886`), and the count carries an explicit `r.tenant_id = $1` (lesson 36). Rotation bypass is closed because `session_id` is server-set by Conversation, not a model argument; a second chain in the same session counts prior runs because the count is per `(tenant, custom_api_id, session_id)` and not per run; a failed/refused step takes no claim and makes no upstream request. `unavailable` (not `invalid_argument`) is the right status — it does not invite the model to retry with new arguments.
- **F4 (low, shared Google grant) — CLOSED.** `oauth_connections.provider_sub` is stored from the same token/user-info response (no extra provider call), its index is deliberately non-unique and non-tenant-scoped (lesson 3 — a unique index here would be a cross-tenant DoS on connecting the same account), the `EXISTS` probe takes `provider_sub` from the `FOR UPDATE` row of the disconnecting connection and never from a request field (lesson 31), `$3` is the path tenant that already passed awaited `assert_tenant_access`, and it runs on `platform_conn` so the RLS bypass is explicit. NULL `provider_sub` revokes anyway, which is the correct fail direction for a revoke. The `shared_grant` response field was correctly *not* added. One residual channel survives — see new finding 1.
- **F5 (low, `env:`/`k8s:` refs) — PARTIALLY CLOSED, and the remainder is an acceptable acceptance.** Writes are closed: `allow_pointer_schemes: bool` is required with no default, the literal `allow_pointer_schemes=is_platform_scoped(current_user)` is specified at each of the eight create/update routes rather than only in prose (lesson 32), `is_platform_scoped` is the scoping predicate and not the role (lesson 24 — confirmed at `services/config/deps.py:105`), `telephony_configs._normalize_one` applies it per credentials entry, and `custom_apis.auth_config` accepts no pointer from anyone. Existing tenant-written Config pointers are explicitly accepted, with the reasoning (env names are platform-global today, so the tenant gets a credential the platform already pays for, not another tenant's data) and with a stated unacceptability condition (the first per-tenant env var or k8s path makes the same pointer a cross-tenant read, and the sweep must ship with it, not after). That is a legitimate accepted residual, not an unmitigated flaw.

## Findings

1. [low] `disconnect`'s `{"revoked": bool}` — and its latency — vary with another tenant's state, so the shared-grant check the design deliberately kept out of the response body leaks through the response anyway — design Interfaces, "`disconnect` (AC8)".
   Attack: an admin in tenant B who controls a Google account connects it, immediately disconnects, and reads `revoked`. For Google the upstream revoke normally succeeds, so `revoked: true` means "no other Yuviz tenant holds a `connected` row for this `(provider, provider_sub)`" and `revoked: false` means "some other tenant does" (or the revoke failed — but the skipped path also returns in milliseconds instead of after a 10s-timeout HTTP round trip, which separates the two). B learns that an unnamed other tenant has the same provider account connected: a cross-tenant existence inference from a response that varies with another tenant's state, which is exactly the lesson-2 property the design cites when it refuses the `shared_grant` field. The leak is narrow (B must control the Google account, and no tenant is named), hence low.
   Fix: make the response independent of the revoke outcome — return the local disconnect result and drive the "also remove Yuviz in your provider account" UI hint from provider capability (Microsoft has no revoke endpoint) rather than from this call's outcome; keep the detail in the existing `oauth_revoke_skipped_shared_grant` log line.

2. [low] `allow_pointer_schemes` has a fifth call site the design does not enumerate, and a required keyword only forces the implementer to find *a* value (lesson 32) — `scripts/seed_default_config.py:103,108`, against design Interfaces, "Config credential tables" ("exactly one expression may feed it … at each create/update route").
   Attack: no attacker on this path directly — the exposure is the repair. `seed_default_config.py` calls `provider_configs.update_provider_config(...)` and `create_provider_config(...)` with no credential arguments, so the new required keyword makes fresh-install seeding `TypeError` at setup time; the implementer's cheapest repair is to give the service functions a default, which silently restores a permissive value on all eight routes. The design's claim that only one expression can feed the keyword is a hand-made enumeration (lesson 29) on a codebase where exactly that has been wrong three times.
   Fix: name `scripts/seed_default_config.py` in the Changes table with the literal it must pass (`allow_pointer_schemes=True`, since the script *is* the platform operator), and state that the service-layer keyword keeps no default; back it with the same mechanical walk the masking test already uses — assert every caller of `resolve_api_key_input`/`_normalize_credentials` passes the keyword explicitly.

3. [low] The quarantine transaction has no blast-radius ceiling, so one run can null every credential in five tables — design Interfaces, "Existing rows", *Quarantine*.
   Attack: a read-only **viewer** in tenant A who is also an admin in their own tenant B reads A's unmasked `api_key_ref`/`auth_token_ref` today (this is the pre-deploy state the masking fix closes) and pastes the exact ciphertext onto B's rows. At migration the script sees the string under two tenants and quarantines *every* occurrence — including A's live production carrier and provider credentials — taking A's calling and DID provisioning offline until an A admin re-enters every key. A viewer thereby causes a destructive write in another tenant. The same ceiling covers the no-attacker variant with the larger blast radius: if the operator runs the script with a `SECRET_ENCRYPTION_KEY` that differs from the services', *every* ciphertext lands in the "fails to decrypt" quarantine class and the whole platform's credentials are nulled in one committed transaction.
   Fix: add an abort threshold — `--max-quarantine N` (and/or refuse to proceed when the undecryptable count is a majority of the inventory), defaulting to a value the operator must raise deliberately after reading the `--dry-run` counts; the existing `--report` then drives the per-tenant rotation notice.

## Verified controls
- Round-4 F1 quarantine: five-column coverage, exact-old-string conditional `UPDATE` with zero-rows aborting the transaction, `SHARE ROW EXCLUSIVE` over all five tables, one transaction, `VALIDATE CONSTRAINT` inside it, exit 1 unless `remaining == 0 AND config_shared == 0`, counts-only stdout, 0600 post-commit JSONL report with ids but no ciphertext or plaintext.
- `"quarantined"` fails closed at all three readers I traced (`secret_resolver.py:85-98`, `did/provider_manager.py:92`, `telephony/accounts.py:138`) — it is truthy, so the "no credential configured" silent-degradation path is genuinely avoided.
- Attribution reasoning is sound and checkable: `audit._redact` (`services/config/audit.py:27`) has never let `api_key_ref`/`auth_token_ref` into `audit_log`, so no dating evidence exists and indiscriminate quarantine is correct, not lazy.
- `_CONFIG_REF_COLUMNS` is a single declaration driving both scan and writes, tripwired against `information_schema.columns` (lesson 29/42) — the mechanical enumeration that rounds 3 and 4 were missing. `carrier_account_ref` is excluded with a stated reason (Twilio account SID, never resolved through `secret_resolver`), and the tripwire forces a re-decision if a new ref column appears.
- Carriers masking is complete across list/get/create/update, the DID service keeps the sealed value through the `is_service_account AND tenant_id IS NULL` exemption (lesson 24), and the route-walking masking test runs one case as that account so an over-broad mask also goes red.
- `carriers.get_carrier_by_id` selects `platform_conn` only when `platform_scoped`, so the one cross-tenant carrier read is not reachable by a tenant principal.
- WhatsApp recipient: `source='caller_id'` params never enter the model's tool schema — verified at `services/conversation/tools/policy_resolver.py:254` (`p.source = 'caller'` join predicate). `value_prefix` and `value_digits_only` are CHECK-bound to `source='caller_id'` and are not exposed on `CustomApiParamSpec`, so both stay preset-only.
- Send cap counts against real columns: `api_chain_steps.session_id` exists and is written from `request.session_id` at every `_record_step` call site, `success` is recorded only after a 2xx (`executor.py:886`), the count carries an explicit `r.tenant_id = $1`, empty `session_id` fails closed, and the refusal precedes both the claim and the upstream request.
- Shared-grant probe: `provider_sub` from the disconnecting row's own `FOR UPDATE` tuple (never a request field), `tenant_id <> $3` with `$3` the authorized path tenant, `EXISTS` returning a boolean and no row, non-unique non-tenant-scoped index so tenant B cannot block tenant A from connecting the same account (lesson 3), NULL `provider_sub` revokes anyway.
- Pointer-scheme gate: required keyword with no default, the literal `is_platform_scoped(current_user)` written at each route (lesson 32), `is_platform_scoped` is `tenant_id is None` and not a role check (lesson 24), reads untouched so no live row breaks at deploy, `custom_apis.auth_config` accepts no pointer from any principal.
- Nothing in rounds 1-3's verified list regressed in the revised text: tenant-bound `enc:t1.` AEAD with the row's own `tenant_id`, `decrypt_secret` refusing `enc:t1.` for the four shared-resolver services, byte-identical-under-`FOR UPDATE` update rule on all four Config tables, create rejecting client `enc:` and `"[stored]"`, OAuth state single-use via one conditional `UPDATE … RETURNING`, composite FK `(oauth_connection_id, tenant_id)`, the confirmation and claim gates, form-body-only secrets with `httpx`/`httpcore` quieted, outbound/inbound direction handling with own-DID fail-closed, Sheets `valueInputOption=RAW`, and 404 parity on `disconnect` for an absent vs. another tenant's id (lesson 2).
- Noted residuals that are correctly bounded and do not need action: a WhatsApp send that is dispatched but recorded `timeout` does not increment the cap, so a platform retry can exceed three actual messages — but every one of them goes to the caller's own number, so only tenant spend is affected; and a tenant admin can always hand-register an uncapped `custom_apis` row with a `source='caller'` recipient, which is tenant self-harm and the pre-existing custom-API trust model, not the anonymous-caller abuse the finding named.
