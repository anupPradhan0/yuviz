# PRD: Connector Presets + Per-Tenant OAuth2 (Authorization Code)

## Problem
A clinic or small-business owner who wants voice booking today has to hand-author a `custom_apis` row per endpoint in `services/toolexec` — an endpoint URL, a JSON parameter schema, upstream chaining, and a success template — none of which a non-technical owner can do. Separately, the only auth schemes toolexec supports (`api_key`, `bearer`, `oauth2_client_credentials`) cannot represent Google Calendar, Zoho, or Microsoft/Outlook, which require a human to click "Allow" once (authorization-code flow) and issue a refresh token scoped to that one tenant. The gap is usability and one missing auth scheme, not the execution engine: booking stays on `execute_api`.

## How this is solved elsewhere
Retell ships no calendar toggle at all — Google Calendar booking is a hand-written custom function backend the tenant hosts themselves (unverified beyond docs/blog description); this is exactly the DIY burden this PRD removes. Vapi and Bland both converged on a "Connect <provider>" button per tenant that runs a real OAuth authorization-code flow and stores a per-tenant token, with Vapi additionally supporting a multi-connection model (Nango `authorizationId`) for platforms managing many end-customers' calendars from one Vapi account — the fork in the road is exactly our shape: one OAuth connection per tenant, selected at call time by the caller's tenant_id, not a single platform-wide connection. Synthflow's "Real-Time Booking Node" is the closest analogue to preset #2: pick a calendar backend (Cal.com is their most-polished path, Google Calendar and Outlook also supported), and the platform pre-wires availability-check → book as a configured action rather than the tenant writing a schema. Two things carry over directly: (1) the connect-once, reuse-everywhere OAuth button, which we adopt: a tenant connects one calendar account and every preset instance built from it shares the connection; (2) presets as pre-wired multi-step chains behind a single dropdown choice, which we adopt for Google Calendar, WhatsApp, and Sheets. One thing we deliberately do not follow: none of the four surface raw OAuth scope/redirect-URI configuration to the tenant — that stays admin/platform-owned, never a form field a clinic owner fills in, which matches this PRD's "no developer" goal.

## Scope

Assumption: "connector" in the request means an OAuth2 provider connection (Google, Zoho, Microsoft) — a new object distinct from an unauthenticated `custom_apis` row — and a "preset" is a template that, when applied, creates one or more `custom_apis` rows (and their chaining) pre-filled for that provider, optionally pointed at a connector for auth.

- In: A tenant admin can click "Connect Google Calendar" (and Zoho, Microsoft/Outlook) from the console, complete the provider's consent screen, and land back with a named, working connection — no manual client-secret entry beyond what registering an OAuth app with the provider requires once, platform-wide, per provider (Assumption: the OAuth app's client_id/client_secret is a platform-level credential registered once by Yuviz with each provider, since asking a clinic owner to create a Google Cloud project defeats the "10 minutes, no developer" goal — this is the same shape Vapi and Bland use).
- In: A tenant admin can disconnect a connector at any time; disconnecting immediately revokes the refresh token with the provider and disables every custom API that depended on it.
- In: A tenant admin can browse a short list of connector presets (Google Calendar booking; WhatsApp confirmation via Gupshup, Interakt, or Meta Cloud API; Google Sheets lead capture) and apply one with a single click, which creates the linked `custom_apis` rows (check-slots → book → reschedule → cancel for the calendar preset, using the existing `upstream_api_id` chaining) already attached to the right connector, and makes them selectable in the Appointments step of an agent's call flow.
- In: Every preset ships default success templates that read back 2–3 slots, not the raw API payload, and a booking preset's chain requires a caller-supplied idempotency key so a retried tool call cannot double-book (see Acceptance Criteria).
- In: The SSRF guard (`resolve_and_validate_endpoint`) and the tenant-namespaced credential-ref discipline (`validate_tenant_ref`) are extended to cover OAuth token/authorization endpoints and preset endpoints exactly as they cover hand-registered ones — no preset or OAuth code path bypasses either.
- In: OAuth tokens (access and refresh) are never shown in the console, never appear in a transcript, call log, or audit row, in full or in part.
- Out: A Yuviz-hosted scheduler API for clinics with no existing software of their own. This is explicitly deferred to a follow-up PRD — it is a new service (not a connector or a preset) and changing scope here would block this PRD's "in about 10 minutes" goal on a much larger build. A clinic with no calendar/CRM software cannot go live with real booking under this PRD; they can still use the WhatsApp confirmation and Sheets lead-capture presets, which need no upstream software.
- Out: Zoho Bookings, Cal.com, Practo, and KareXpert presets. Only Google Calendar booking, WhatsApp confirmation, and Google Sheets lead capture ship now; the other four are named as future presets once this connector/preset mechanism is proven. Zoho and Microsoft/Outlook connectors (the OAuth connection itself) do ship now even though their booking presets do not, so the connector layer is exercised by more than one provider from day one.
- Out: `oauth2_client_credentials` is unchanged. This PRD adds a new `oauth2_authorization_code` scheme alongside it; it does not touch or migrate the existing scheme.
- Out: Editing a preset-created `custom_apis` chain's parameter schema or chaining in the raw custom-API editor is not blocked by this PRD, but is called out as an open question below, since an owner who edits a preset-generated API loses the guarantee that it stays preset-shaped.

## Acceptance criteria

**Connecting a provider**
1. Given a tenant admin on the connectors screen, when they click "Connect Google Calendar", then they are redirected to Google's OAuth consent screen with a `state` parameter bound to their tenant and a PKCE `code_challenge`, and no client secret is visible to them at any point.
2. Given a tenant admin completes consent and Google redirects back with a valid `code` and matching `state`, when the callback is processed, then a connection row is created scoped to that tenant, storing the access token and refresh token as tenant-namespaced secret refs (never as plaintext columns), and the console shows the connector as "Connected" with the connected account's email/name, never the tokens.
3. Given a callback arrives with a `state` value that does not match one this backend issued (forged, replayed, or expired), when it is processed, then the connection is rejected, no token exchange is attempted, and the tenant sees a generic "connection failed, please try again" message.
4. Given a callback arrives with a `code` but the PKCE `code_verifier` does not match the `code_challenge` from step 1, then the token exchange fails and no connection is created.
5. Given a redirect URI in an incoming OAuth callback that is not the platform's own registered callback URL, when the authorization request is built, then the request is rejected before redirecting the tenant — the redirect URI is never taken from tenant input.
6. Given an access token has expired, when a custom API using that connector is called, then the refresh token is used to obtain a new access token automatically, with no tenant action required, and the new access token replaces the old one in tenant-namespaced storage.
7. Given a refresh attempt fails because the provider has revoked or expired the refresh token, when a custom API using that connector is next called, then the call fails with a clear "reconnect required" error surfaced to whoever is diagnosing the failed call, and the connector's console status changes to "Reconnect needed" — not to a value indistinguishable from "Connected".
8. Given a tenant admin clicks "Disconnect" on a connected provider, when the disconnect completes, then the provider's revoke endpoint is called for that token, the tenant-namespaced secret refs are deleted, the connection row is marked disconnected, and every `custom_apis` row that referenced it is disabled (not deleted) so the agent stops calling it rather than calling it with a dead credential.
9. Given tenant A has a connected Google Calendar and tenant B does not, when tenant B's console loads the connectors screen or tenant B's agent runs a call, then no code path can resolve, display, or use tenant A's connection or tokens — verified by an explicit `tenant_id` predicate on every read of the connection/token storage, not RLS alone (existing tenant-isolation discipline; see Constraints).
10. Given tenant A and tenant B each have their own connection to the same provider (e.g., both connected Google Calendar) and both refresh at the same time, when the refresh/rotation write persists the new access token, then the UPDATE is a single conditional statement scoped by both `tenant_id` and the connection's own id in its WHERE clause (`UPDATE ... WHERE tenant_id = $1 AND id = $2 ... RETURNING *`, never connection id alone) — so tenant A's refresh can never read, overwrite, or lose a race against tenant B's row, and two concurrent refreshes of the *same* tenant's own connection cannot corrupt it into a torn write (lesson 8: check-then-act on a shared row is a race).
11. Given any connector's access or refresh token, when it flows through a log line, an audit row, a transcript, or a console response body, then the token value is absent or redacted in every one of those sinks — verified for the OAuth callback handler, the refresh path, and the executor's use of the resolved token, matching the "never once in a step row, log line, or arguments hash" discipline `auth_schemes.apply()` already applies to `api_key`/`bearer`/`oauth2_client_credentials`.
12. Given an OAuth authorization or token endpoint URL (provider-supplied, not tenant-supplied) is dialed by the backend, when the SSRF guard's endpoint validation runs, then it applies the same host/scheme/private-IP checks `resolve_and_validate_endpoint` already applies to tenant-registered `custom_apis.endpoint_url`.

**Connector presets**
13. Given a tenant admin with a connected Google Calendar, when they select the "Google Calendar booking" preset and confirm, then four `custom_apis` rows (check-slots, book, reschedule, cancel) are created in one transaction, pre-filled with endpoint, parameters, chaining (`upstream_api_id` wiring check-slots → book), auth pointed at the tenant's connector, and a success template — with no field left for the tenant to fill in before the preset is usable.
14. Given a preset-created custom API set exists, when the tenant opens the Appointments step of an agent's call flow, then those APIs are selectable there without any additional custom-API configuration step.
15. Given a tenant applies the "Google Calendar booking" preset without a connected Google Calendar, when they attempt to apply it, then the preset flow first prompts them to connect Google Calendar and only creates the custom APIs after a successful connection.
16. Given the WhatsApp confirmation preset (Gupshup, Interakt, or Meta Cloud API — tenant picks one), when applied, then it creates a `custom_apis` row using `api_key` or `bearer` auth (per that provider's own scheme, not OAuth) with the tenant's WhatsApp Business API credential entered once during preset setup, referenced the same tenant-namespaced way as any hand-registered credential.
17. Given the Google Sheets lead-capture preset, when applied with a connected Google account, then it creates a `custom_apis` row that appends a row to a sheet the tenant selects (or a Yuviz-created default sheet) during setup.
18. Given a tenant deletes (soft-deletes) a connector that a preset-created `custom_apis` row still references, when the deletion is attempted, then it is blocked or cascades to disabling those rows exactly as an existing "dependent API exists" conflict does for `upstream_api_id` dependents (`DependentApiExists`) — the tenant is never left with a live, enabled row pointing at a dead connector.
19. Given a tenant disconnects a provider (disabling its preset-created `custom_apis` rows per AC8) and later reconnects the same provider, when reconnection completes, then preset apply for that provider is idempotent per tenant: the existing disabled rows are repointed to the new connection and re-enabled, rather than a second set being created — reconnecting never produces two rows colliding on `custom_apis_tenant_name_key` (`database/schema.sql:882-883`), and this repoint-not-duplicate behavior is the same one AC18's cascade must leave rows in a state to receive (disabled, not soft-deleted).
20. Given a preset's endpoint URLs (provider API base URLs), when registered by the preset-apply code path, then they pass through the same `resolve_and_validate_endpoint` SSRF check as any tenant-typed endpoint — no preset is exempt because Yuviz authored the URL.

**Voice-specific booking behavior (Google Calendar booking preset)**
21. Given the check-slots step of the booking chain, when the agent calls it, then the success template renders at most 3 available slots as spoken-friendly text (e.g., "10 AM, 11:30 AM, or 2 PM"), never a raw list of every open slot in the queried window.
22. Given a caller has verbally agreed to a specific slot but the book step has not yet been called, when the call flow reaches the book step, then the flow requires an explicit prior confirmation turn (read back name, doctor/service, and time; caller says yes) before the book API is invoked — enforced as a call-flow design requirement on the Appointments step, not left to prompt wording alone.
23. Given the same call is retried or times out and the agent (or the platform's own retry logic) calls the book step again for the same booking attempt, when the second call reaches the upstream calendar API, then it carries an idempotency key derived from the call id and the booking attempt, and the upstream request is deduplicated so no double-booking occurs — exercising `custom_apis.idempotency_header` on the book step of every generated preset.
24. Given a check-slots lookup takes longer than about 700ms, when the caller is waiting, then the call flow plays one of the existing filler phrases rather than dead air — reusing the existing filler-phrase mechanism, not a new one.

**Permission and failure paths**
25. Given a console user without tenant-admin privileges, when they attempt to connect, disconnect, or apply a preset for a connector, then the action is rejected with the same role-check discipline other tenant-scoped mutations in this console already use.
26. Given the OAuth provider itself is unreachable or returns an error during token exchange or refresh, when this happens, then the tenant sees a clear, non-technical error and no partial connection row or partially-created preset chain is left behind (the create is transactional, matching `create_custom_api`'s existing per-tenant advisory-locked transaction pattern — verified against `services/toolexec/custom_apis.py:508`, which takes `pg_advisory_xact_lock(hashtext('custom_apis:' || tenant_id))` before writing).

## Constraints
- New auth scheme `oauth2_authorization_code` extends `custom_apis.auth_scheme`'s CHECK constraint (`database/schema.sql:866-867`) alongside `none`/`api_key`/`bearer`/`oauth2_client_credentials`; it must follow the same `_CREDENTIAL_REF_FIELDS` / `_validate_credential_ref` discipline in `services/toolexec/custom_apis.py:156-177` and the same tenant-namespaced-ref resolution in `services/toolexec/auth_schemes.py` (`validate_tenant_ref` / `resolve_tenant_ref`) — refresh tokens are exactly the kind of tenant secret that module exists to protect, and its own module docstring already states the rule: validated both at registration and again at resolution, keyed off the row's own `tenant_id` (`services/toolexec/auth_schemes.py:14-18`).
- The connector object (provider, account identity, token refs) is new state distinct from `custom_apis` and needs its own tenant-scoped table with the same `tenant_id NOT NULL REFERENCES tenants(id)` and partial soft-delete index pattern `custom_apis` uses (`database/schema.sql:858-884`).
- Every existing SSRF and credential-ref control is a call-time control, not a registration-time-only one (`services/toolexec/custom_apis.py:4-9`, `auth_schemes.py:14-18`) — the OAuth authorization endpoint, token endpoint, and refresh endpoint must run through the equivalent of `resolve_and_validate_endpoint` even though they are provider URLs, not tenant-typed ones, because DNS rebinding and misconfiguration apply regardless of who wrote the URL.
- Per lesson 36, RLS on any new connector/token table cannot be the only protection, because this codebase's services still connect with a BYPASSRLS role — every read AND write of the new table needs an explicit `tenant_id = $N` predicate in the query itself (see AC9 for reads, AC10 for the refresh/rotation write), in addition to whatever RLS policy is added.
- The refresh/rotation write is a check-then-act race by default (read the current token, call the provider, write the new one) — per lesson 8, implement it as a single conditional `UPDATE ... WHERE tenant_id = $1 AND id = $2 [AND refresh_token_ref = $3] ... RETURNING *` and treat zero rows returned as "someone else already refreshed this connection, re-read and use their result" rather than as an error.
- Tokens must never be logged: follow `auth_schemes.apply()`'s existing pattern of returning only the set of header/query-param *names* it injected, never values, so callers (executor.py, audit.py) cannot accidentally persist or hash the resolved secret (`services/toolexec/auth_schemes.py:163-168`).
- `agent_custom_apis` (which of a tenant's custom APIs an agent may call) is unchanged by presets — preset-created rows are ordinary `custom_apis` rows and go through the same enable/attach step to an agent (`database/schema.sql:919-932`).
- The console client for this area is `admin-ui/lib/toolexecApi.ts`, following its existing pattern of a typed request wrapper against the toolexec service's own base URL and the shared console JWT (no separate login) — new connector/preset endpoints belong in this same client, and any new UI belongs alongside `admin-ui/components/CustomApisPanel.tsx` / `AgentCustomApisPanel.tsx`, not a new admin app.
- `idempotency_header` already exists on `custom_apis` (`database/schema.sql:870`); the booking preset's "book" step must set it, not invent a parallel idempotency mechanism.
- Chain depth for the calendar preset (check-slots → book → reschedule → cancel, with reschedule/cancel independently chained off check-slots or book as needed) must respect the existing `graph.MAX_CHAIN_LEVELS` (4) ceiling enforced in `_recompute_tenant_chain_levels` (`services/toolexec/custom_apis.py:11-19`).

## Open questions
1. Who registers the platform-level OAuth app (client_id/client_secret) with Google, Zoho, and Microsoft — is this a one-time manual setup task per provider done by Yuviz before launch, or does it need an admin console screen of its own? Changes whether this PRD needs a platform-admin (not tenant-admin) settings surface.
2. Should a tenant be allowed to edit the parameter schema, chaining, or success templates of a preset-created `custom_apis` row in the existing raw custom-API editor, or should preset-created rows be read-only/locked to preserve the "it just works" guarantee? Changes whether the editor needs a new "preset-managed, edit at your own risk" state.
