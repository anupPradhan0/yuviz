1. [blocking] The override branch throws away the usable deferred voice and speaks the language with the base voice's pronunciation — `services/conversation/provider_bundle.py:99-111` — fails when: a multilingual en+hi agent has a Hindi Kokoro override, the Kokoro weights are not on disk, and neither the base voice (for example English Kokoro, or an English-only cloud voice) nor the default speaks hi. Result: the error branch `continue`s, tts_for("hi") returns the base voice, and Hindi text goes through English G2P. When the base is not Kokoro, nothing ever downloads the weights, so this repeats on every call. `inst.provider` (a defer_load KokoroTTS that would fetch the weights off the loop) was available — fix: in that else-branch set `tts_by_language[lang] = inst.provider` when it is not None, matching _get_or_default.
2. [minor] Kokoro's ready path still builds KPipeline/KModel (torch.load of the ~330 MB .pth, plus misaki G2P init) synchronously on the event loop — `services/conversation/ai_provider_manager.py:189-193` — fails when: a new Kokoro row is first resolved mid-traffic (cache miss after invalidate, or a new agent). Every live call on the process stalls for the load time (about 1-3 s). This was already the case on main, not a regression — fix: return `KokoroTTS(..., defer_load=True)` here too, or build it with `asyncio.to_thread`.
3. [minor] Not-ready Kokoro instances are neither deduplicated nor cached (unlike `_not_ready_whisper`) — `services/conversation/ai_provider_manager.py:184-188` — fails when: N concurrent calls hit a Kokoro agent whose default can't serve while the weights are missing. Each call gets its own deferred KokoroTTS, and each first synthesis loads its own KModel (about N × 350 MB RAM) after the shared download — fix: keep one deferred instance per (voice, lang_code, speed) the way `_not_ready_whisper` does.
